# 联调模式规范（DEBUG MODE）

> **仅在用户声明「开始联调」时生效**；用户声明「结束联调」即退出该模式。
>
> 生效期间：**本文件优先于项目规范**（`docs/*` 与记忆里的规范条目）。本文件没写到的，按项目规范执行；
> 本文件写到的，一律以本文件为准。**修复问题永远优先于守规范**。
>
> 进入/退出用语：**「开始联调」** / **「结束联调」**（用户声明）

## 0. 进入时立刻做（三步，别做多余的事）

1. **必须新开分支**：从 `main` 切 `debug/<主题>`（主题用小写短横线，如 `debug/ws-reconnect`）。
   —— 不与其他工作混在同一分支。
2. **建需求文件**：`docs/debug/<主题>.md`（模板见 §2）。
3. **先复现**：照用户给的现象，用最小的操作把它复现出来；复现不了就先补日志/加探针再复现。

## 1. 模式目标（第一优先级）

- **优先修复用户提出的 bug、或新增用户要求的功能**，其余一律让路。
- **减少思考、快速定位**：不做过度的方案推演、不做无关重构、不顺手清理代码。
  「先抓到现象 → 再定位断点 → 再改一处」。
- 为了修好问题，**可以不遵循项目规范**（提交粒度、注释/类型规范、目录约定、TODO 同步等都可放宽），
  **但无论如何必须遵循本文件**（新分支 + 需求记录 + 请求记录 + 结束时可复现）。

## 2. 需求记录（必须）：`docs/debug/<主题>.md`

用这个骨架（缺哪项就补哪项，不要留空项）：

```markdown
# <主题>（YYYY-MM-DD）

## 需求

- 用户原话 / 要修什么 / 期望行为：

## 复现步骤（照做就能复现）

1. 前置条件（服务/设备/broker/配置项取值）
2. 操作（HTTP 请求 / MQTT 上报 / 前端动作）
3. 观察到的现象：
4. 期望现象：

## 现场信息

- 设备 `d_no`、相关配置项（`direct_config` code + 取值）、时间点、涉及的提交/分支

## MQTT / HTTP / WS 请求记录

- MQTT（主题 / payload / 出站帧）：
- HTTP（请求行 + query/body + 响应摘要）：
- WS（`data` / `alarm` / `direct` / `lock` 事件；带 `goal` 区分连接）：
- 原始记录路径：`tmp/debug/<主题>/`（见 §3）

## 定位与修复

- 复现后定位到的断点/根因：
- 改了哪些文件、为什么：
- 验证结果（命令 + 输出结论）：

## 状态

- [ ] 进行中 / [ ] 已修复待验证 / [ ] 已验证
```

## 3. 请求记录（必须，保证结束时可复现）

- **要记什么**
  - MQTT：入站主题 + payload、出站 `MQTT_PUBLISH`（含 `control/` Modbus 帧）
  - HTTP：请求行 + query/body + 响应摘要（状态码、`success`、关键字段）
  - WS：上行消息 + 下发的 `data`/`alarm`/`direct`/`lock`（可用 `goal` 区分连接）
- **落在哪**
  - 关键报文**摘录进 `docs/debug/<主题>.md`**（入库、长期留痕）
  - 原始记录（完整报文/日志/抓包）落盘到 **`tmp/debug/<主题>/`**，gitignore，不进库；
    md 里写明该路径 + 用的抓取命令
- **怎么抓**（按需选用，若本机没装对应工具就用 `tmp/` 下的临时脚本）
  - 服务日志：服务启动日志与 `logs/`、`tmp/server*.log`（MQTT 入站/出站、WS 推送都有打印）
  - HTTP：`curl -i` 或浏览器 devtools；把命令与响应贴进 md
  - MQTT：broker 订阅脚本 / `tmp/` 临时订阅脚本
  - WS：用现有 E2E 客户端脚本（`tests/e2e/*.mjs`）或 `tmp/` 临时连接脚本
  - 必要时给链路加**临时日志**（等级见 §4）
- **收尾前必须自检**：照 md 的「复现步骤」+ 记录，**能再次复现原问题（或证明修复）**；
  做不到就说明记录还不够，继续补。

## 4. 允许的操作范围（本模式放宽）

- **可恢复前提下，允许操作项目内任何文件**（包括平时不动的 `core/**`、`types/**`、
  `gateways/**`）；也允许为造场景临时改配置 / 种子 / 数据库行。
- **允许向任何地方加日志**（含临时 `console`），用于快速拿到复现信息。
  但**必须注意日志等级**：
  - 高频路径（每帧数据、每笔入站报文）→ `debug`（不要用 `info` 刷屏）
  - 关键分支/状态迁移（判定命中、锁变化、下发指令）→ `info`
  - 异常与失败 → `error`；临时排障信息不要长期留在 `info`/`error`
- 允许写临时脚本：放 `tmp/`（一次性）或 `tests/e2e/`（打算长期入库）。
- **「可恢复」是硬要求**：动手前先想好怎么回滚（新分支 / `git stash` / 记录 SQL / 备份文件），
  所有为造场景做的改动**必须写进 md**（改了哪个库/表/行、怎么还原）。
- 仍然生效的红线：**未经用户明确要求，不写入/修改「规范」类记忆**（见项目规范）。

## 5. 收尾清单（用户说「结束联调」时逐条执行）

1. 补齐 `docs/debug/<主题>.md`：复现步骤、三类请求记录、根因与修复、验证结果、状态勾选。
2. **清理临时排障物**：降级/删除临时日志与探针；还原为造场景改过的配置 / 种子 / DB 行 / 文件。
3. 跑能跑的校验并写进 md：`pnpm type-check`、`pnpm test`；涉及链路的跑对应 `tests/e2e/*`。
4. 在 `debug/<主题>` 分支提交，提交信息写清「**修了什么 + 怎么复现 + 怎么验证**」。
5. **不自动合并 `main`**，也不删分支 —— 等用户审查后决定（合并/删除）。
6. 汇报：改了哪些文件、临时物是否已清、`docs/debug/<主题>.md` 与原始记录路径、记忆是否改动。

## 6. 与项目规范的关系（覆盖表）

| 项目规范条目                    | 联调模式下                                                       |
| ------------------------------- | ---------------------------------------------------------------- |
| 大改动先方案后动手              | **放宽**：直接动手，只需一句话说明在做什么                       |
| 每步只做一件事 / 重构与功能分离 | **放宽**：以修好为优先，允许一提交里混合                         |
| 提交粒度与提交信息格式          | **放宽**：信息写清「问题 + 复现 + 验证」即可                     |
| 分支策略（`feat/*`，审后合）    | **覆盖**：必须 `debug/<主题>` 新分支                             |
| `src/types/` 禁止外部引用       | **放宽**（可恢复前提）；收尾时若改动要留下，按项目规范收拾或回滚 |
| `docs/TODO.md` 同步             | **放宽**：本期记录改在 `docs/debug/<主题>.md`，收尾按需回写      |
| 临时文件放工作区 `tmp/`         | **保持**（原始请求记录也放 `tmp/debug/<主题>/`）                 |
| 校验要跑全仓 lint/类型/单测     | **放宽**：以定位为主，收尾时必须跑一遍                           |
| 未经同意不得写入「规范」类记忆  | **保持**（红线）                                                 |

## 7. 一句话版本

**开 `debug/<主题>` 分支 → 在 `docs/debug/<主题>.md` 记需求与复现步骤 → 抓 MQTT/HTTP/WS 记录
（原始件放 `tmp/debug/<主题>/`）→ 加日志快速定位 → 修 → 收尾时清理临时物、跑校验、提交到该分支、
保证照记录能复现。**
